This guide is the fast path to a sound workflow. It assumes you know the
[data model](/reference/data-model/); here we focus on the decisions that make a
workflow *work* rather than just validate. The authoritative, code-referenced
rules live in the [reference](/reference/data-model/) and in the downloadable
[`schema_conventions.md`](/examples/schema_conventions.md).

<Aside type="note">
This system is a price / economic monitor that produces trading insight. Every workflow should collect real market, macro, news, or social evidence and reason over it — not run a topology-only or abstract exercise.
</Aside>

## 1. Sketch the roles, then the graph

Decide the **functionary roles** first: a collector, an analyst, a critic, a
synthesizer. Each role becomes one agent node. Then decide how evidence flows
between them — that's your `data_flow` edges.

Give each node a `label` that is a **tight role**, not a task sentence:
`Data Collector`, `Risk Critic`, `Briefing Synthesizer`. The label is the
model's anchoring task at runtime, so keep the actual procedure out of it (see
step 3).

## 2. Give each agent exactly one tool node it needs

An agent can only call a tool if a `tool_call` edge connects it to a **tool
node**, and the tool node lists the callable tools in its `config.tools`. The
calling agent keeps `config.tools: []`.

- Put a collector's fetch tools (`fetch_exchange_data`, `fetch_macro_data`,
  `fetch_news_data`, `fetch_social_media_data`) on one tool node.
- Put an analyst's text tools (`summarize_text`, `score_text`, …) on a separate
  tool node when a different agent calls them.

Browse the full [tool catalog](/reference/tool-catalog/) for what's available.

## 3. Write 3–5 imperative instruction bullets per agent

Instructions are the procedure. Each bullet must earn its place:

- **Name the exact operation and arguments.** For example:
  `Call fetch_exchange_data with source_id='okx', source_type='ticker', symbol='BTC-USDT', limit=1.`
- **Fix the output shape.** "Write three parts: setup, one level, invalidation."
- **Require grounding.** "Cite the returned evidence ID in square brackets."
- **Encode the guardrail.** "If no reviewer feedback is present, do not fabricate
  it." Use terminal tokens like `ADEQUATE` or `APPROVED` for critics.

Pin the *interface* (tool, args, output parts, citation); leave the *judgment*
(direction, level, verdict) to the model. Too abstract and it drifts; too
specific and it parrots.

<Aside type="caution">
YAML gotcha: an instruction bullet containing a colon-space (`: `) must be single-quoted, or the YAML parser reads it as a mapping key.
</Aside>

## 4. Give every agent an explicit completion contract

Prefer `mode: explicit` on every agent node. A collector's contract should carry
a machine-checkable `evidence` block — required `tool_names`, `source_ids`,
`source_types`, `data_types`, and `required_fields`. A non-collecting role
(planner, critic, reviewer) uses `evidence: null` — a semantic-only requirement
the judge still enforces.

A downstream analyst can contract against evidence an **upstream** node
collected, as long as the evidence propagates over `data_flow` (source exposes
downstream state, target reads upstream state). See
[Completion contracts](/reference/completion-contracts/) for the reachability
rule and the full evidence-key list.

## 5. Add loops only where revision helps

- A single agent that should iterate on its own output: set
  `agent_loop_default: true` (budget from `WorkflowConfig.max_iterations`), or
  add a self-loop `data_flow` edge carrying `loop_rounds`.
- A multi-node revision cycle (draft → critique → back to draft): add a back
  edge with `loop_rounds ≤ max_loop_rounds`. Keep the cycle single-entry so the
  graph stays reducible.

[Nodes, edges, and loops](/reference/nodes-edges-loops/) has the exact rules.

## 6. Lay it out for readability

There is no auto-layout — you set `position.x` / `position.y`. Flow top-to-down
(producers above consumers, ~180–200px per row), keep a tool ~300px to the side
of its calling agent, and leave the back-edge lane of a loop clear.

## 7. Validate, then run

Validate before shipping — Pydantic load plus `SchemaValidator.validate`
(structure, reachability, loop reducibility). See
[Validation](/reference/validation/). Then run it in the app or drop it into a
self-hosted `schemas/` directory ([Use an example schema](/guides/use-an-example/)).

## Learn by editing an example

The quickest way to learn the shape is to import a
[gallery example](/guides/patterns/) closest to your goal and adapt it: change
the symbols, swap the sources, adjust the contracts. Every example is a working,
validated starting point.
