This guide is the fast path to a workflow that works. It focuses on the decisions
that make a workflow good, not just valid. For the exact rules behind each part,
see the [building blocks](/reference/data-model/).

<Aside type="note">
Price Monitor Agent produces trading insight from real data. Every workflow should collect real market, macro, news, or social evidence and reason over it, not run an empty, abstract exercise.
</Aside>

## 1. Sketch the roles, then the flow

Decide the roles first: a collector, an analyst, a critic, a synthesizer. Each role
becomes one agent. Then decide how evidence should flow between them, and draw a
connection for each hand-off.

Give each agent a short, clear role name, like `Data Collector`, `Risk Critic`, or
`Briefing Synthesizer`. That name is what the agent stays anchored to while it
works, so keep the step-by-step part out of it (see step 3).

## 2. Give each agent the tools it needs

An agent can use a tool only when you connect it to a tool node that carries that
tool. Add a tool node, put the tools on it, and connect it to the agent that should
use them.

- Put a collector's fetch tools (prices, macro, news, social) on one tool node.
- Put text tools (summarize, score) on a separate tool node for the agent that does
  the analysis.

Browse [Tools you can use](/reference/tool-catalog/) for the full list.

## 3. Write three to five clear instructions per agent

Instructions are the procedure. Each one should earn its place:

- **Name the exact action.** For example, fetch the current Bitcoin price from OKX.
- **Fix the shape of the output.** For example, write three parts: setup, one level,
  and invalidation.
- **Require grounding.** For example, cite the evidence you used in square brackets.
- **Set the guardrail.** For example, if there is no reviewer feedback, do not make
  it up. Use a clear finish word for a critic, like `APPROVED`.

Pin the interface (which tool, what output, cite evidence) and leave the judgment
(direction, level, verdict) to the model. Too vague and it drifts; too rigid and it
parrots.

## 4. Give every agent a success rule

Give each agent a clear rule for what counts as done. A collector's rule should
require real evidence: the right data, from the right source, with the fields you
need. A role that does not collect, like a planner or critic, can be judged on the
quality of its answer instead.

A later agent can be held to a rule about evidence an earlier agent collected, as
long as that evidence flows to it. See [Success rules](/reference/completion-contracts/)
for the details.

## 5. Add loops only where revision helps

- To let one agent improve its own output, turn on its loop and set how many rounds
  it gets.
- For a draft-and-critique cycle across agents, connect a step back to an earlier
  one and set how many rounds it may run. Keep the loop simple, with a single way
  in.

[Nodes, connections, and loops](/reference/nodes-edges-loops/) has the exact rules.

## 6. Lay it out for readability

Arrange the flow top to bottom, with producers above the agents that use them. Keep
a tool node beside the agent that calls it, and leave room for a loop's return path.
A workflow that reads clearly is easier to trust and to change.

## 7. Save, then run

Saving checks your workflow and tells you if anything is wrong. See
[Build checks](/reference/validation/) for what is verified. Once it saves cleanly,
run it in the app, or run it in your own copy ([Use an example](/guides/use-an-example/)).

## Learn by editing an example

The quickest way to learn the shape is to open the
[gallery example](/guides/patterns/) closest to your goal and adapt it: change the
coin, swap the sources, adjust the rules. Every example is a working starting point.
