A success rule (a completion contract) is what makes a node's success earned rather
than claimed.

## `CompletionContract`

| Field | Meaning |
|---|---|
| `mode` | `explicit` requires at least one `requirement`; `disabled` sets no requirements. |
| `requirements` | The list of requirements the node must satisfy. |
| `requires_final_output` | The node must produce a final message. |
| `minimum_output_characters` | Minimum length of that message. |
| `required_output_fields` | Named fields the output must contain. |
| `requires_evidence_citations` | The output must cite evidence. |
| `judge_authority` | `advisory` or `binding`. How the quality judge's verdict is treated (below). |

<Aside type="tip">
Prefer `mode: explicit` on every agent node. A `disabled` contract with only a character minimum means any text of that length passes, which is the opposite of evidence-backed success.
</Aside>

## `CompletionRequirement` and `EvidenceRequirement`

Each requirement has a `requirement_id`, a `description`, and an optional `evidence`
block. Set `evidence: null` for a requirement judged on quality alone (planner,
critic, reviewer); the judge still enforces the description.

An `EvidenceRequirement` is machine-checked:

| Key | Meaning |
|---|---|
| `minimum_items` | Minimum number of evidence items. |
| `minimum_records` | Minimum number of records within them. |
| `tool_names` | Tools that must have produced the evidence. |
| `source_ids` | Required source ids (for example `okx`, `ecb`, `guardian`). |
| `source_types` | Required source types (for example `ticker`, `interest_rates`, `search`). |
| `data_types` | Required data types (below). |
| `required_fields` | Dotted paths that must be present, for example `last` or `0.value`. |

### The `data_type` convention

A `data_type` is the source id and source type joined with an underscore, like
`okx_ticker`. Combinations used by the examples:

| `data_type` | Notable `required_fields` |
|---|---|
| `okx_ticker` | `last`, `high24h`, `low24h`, `vol24h` |
| `ecb_interest_rates` | `0.value` |
| `guardian_search` | none required |
| `lemmy_search` | none required |
| `mastodon_hashtag` | none required |

## Reachability (checked)

A requirement's `tool_names` must be reachable from the node, either:

- directly, through a `tool_call` edge to a tool node that exposes that tool; or
- indirectly, passed over `data_flow` from an upstream collector. This needs
  `expose_downstream_state` on the source node and `read_upstream_state` on the
  target.

This is why a downstream analyst can require evidence an upstream node collected
without owning the tool connection itself, the pattern used in the
[Two-Step Pipeline](/guides/patterns/#two-step-pipeline).

## The quality judge (`judge_authority`)

After the evidence checks pass, a judge evaluates the output against the requirement
descriptions. `judge_authority` decides what happens when the judge cannot return a
valid verdict (for example a truncated response or a provider error):

- `advisory` (default) accepts the candidate if all evidence checks passed.
- `binding` forces an inconclusive or failed result.

Prefer `advisory` unless the work truly needs a hard quality gate.

## Run-level failure policy

`WorkflowConfig.on_node_failure` decides what a node that does not complete does to
the run:

- `continue` (default) records the node and keeps scheduling the rest; the run ends
  `partial` if any node did not complete.
- `fail_fast` stops the run at the first node that does not complete.

A node that runs out of retries becomes a clean `failed` result rather than crashing
the whole run.
