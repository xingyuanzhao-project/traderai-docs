This page covers the node types, the connections between them, how a node's prompt
is built, and the rules for loops and layout.

## Node types

| `node_type` | Role |
|---|---|
| `agent` | One agent: it receives assembled context, calls its model, may issue tool calls, and returns structured output. |
| `agent_group` | A group of sub-agents commanded by an upstream planner; requires `group_config`. |
| `tool` | A holder for callable tools. Its `config.tools` lists the tools it exposes, and agents reach them through a `tool_call` edge. |

### Node naming (`label`)

`label` is the node's anchoring task at run time, not just a display name, so keep
it a tight role:

- **Good:** `Data Collector`, `Risk Critic`, `Briefing Synthesizer`. Tool nodes name
  the capability, like `Exchange Data` or `Market and Macro Data`.
- **Avoid:** a full task sentence as the label. It buries the task in the anchor and
  repeats `instruction`.

## Connections and tool authorization

Connections are called edges in a workflow. There are three types.

| `edge_type` | From and to | Purpose |
|---|---|---|
| `data_flow` | producer to consumer (consumer must be `agent` or `agent_group`) | Carries output and evidence downstream. |
| `tool_call` | `agent` or `agent_group` to `tool` | The only way to authorize a node to call a tool. |
| `synchronization` | executable node to executable node | Co-stages two nodes, so neither advances until both finish. |

Rules that are checked:

- A `tool_call` edge authorizes the calling agent to use the tools listed on the
  tool node. The calling agent keeps `config.tools: []`.
- A `data_flow` consumer must be an `agent` or `agent_group`. Tools receive input
  only through calls.
- Every connection endpoint must exist, and every `node_id` must be unique.

## How a node's prompt is built

At run time, the messages sent to the model are assembled in this order:

1. system prompt (empty for normal nodes);
2. `config.instruction` bullets, as one user message (the procedure);
3. few-shot examples (windowed);
4. upstream data blocks from incoming `data_flow` connections;
5. tool results;
6. `node.label`, as the final user message (the anchoring task, never trimmed).

Design around these facts:

- Put the procedure in `instruction` and keep the role in `label`.
- Upstream data is trimmed largest-first to fit `token_budget`, while the `label`,
  the system prompt, and tool results are never trimmed.

## Loops and iteration budget

There are two kinds of loop.

**Single-node loop**, where a node iterates on its own output:

- `agent_loop_default: true` takes the budget from `WorkflowConfig.max_iterations`,
  with no self-loop needed.
- `agent_loop_default: false` requires a self-loop `data_flow` connection whose
  `loop_rounds` is the budget, or the check fails.

**Multi-node loop**, a cycle across several nodes:

- The back connection carries `loop_rounds`, at most `config.max_loop_rounds`.
- Nested loops are an inner cycle inside an outer cycle. See the
  [Self-Checking Loop](/guides/patterns/#self-checking-loop) example.

<Aside type="caution">
Loops must have a single way in, so the order of work is always well defined. A loop with more than one entry is a build error.
</Aside>

## Layout

There is no auto-layout; the canvas shows your `position` coordinates as they are.

- `data_flow` connections route from a node's bottom port to the target's top port.
- A self-loop arc bulges to the right of the node.
- A `tool_call` connection is a short double-arc between an agent's right port and a
  tool's left port.

Rules that keep a workflow readable:

1. Flow top to bottom: producers above consumers, about 180 to 200px between rows.
2. Put a tool on the same row as its calling agent, offset about 300px to the side,
   not stacked directly below it.
3. Space parallel agents about 320 to 360px apart.
4. If an agent has a self-loop, keep about 100px clear to its right.
5. For a multi-node loop, keep the return lane clear of other nodes.
